# Competitive review and challenged priorities — 2026-10-25

This review expands the earlier five visual, five usability, and five speed recommendations into **25 ranked candidates, including 12 additions to that list**. It promotes object copying and connector editing, separates measured performance costs from proposed fixes, and drops two prematurely chosen solutions. The two earlier additions—representative validation and a current showcase—remain immediate supporting work.

**The strongest missed areas are input navigation, canvas accessibility, quick connected-note creation, source references, retrieval across boards, and image/undo profiling.** More visual effects are a lower priority than making these workflows complete.

This is a research proposal, not a change to the committed [roadmap](roadmap.md). That roadmap already plans labeled connectors and lists object copying, groups, SVG, zoom-to-selection, and URL/file links as candidates. “New” below means added to the preceding recommendation list, not necessarily new to the project's history.

The [2026-10-26 landscape extension](competitive-landscape-2026-10-26.md) adds ten product families, a historical sunset case, multiple comparison filters, niche choices, and essential-feature tiers. Read it first for positioning; retain this report for the detailed 25 proposals.

## Method and limits

Reviewed the current checkout at `896cca8`, its contribution rules, interaction and persistence code, documented benchmarks through 2026-10-25, earlier reviews, current roadmap, and primary documentation or repositories for **13 product families and two Obsidian plugins**. The earlier visual pass in this conversation generated the screenshot suite and inspected representative board states. This research extension did not run another benchmark or install competing applications.

Competitor feature availability is evidence of an established design pattern, not proof that Omarchyform users need it or that the implementation transfers from a browser to Qt. No comparative speed claims, market-share claims, quantified ROI, or implementation-time estimates are made. Vendor documentation establishes described capabilities, not their usability or accessibility quality in practice.

The default audience assumed here is someone using a local, keyboard-first Omarchy canvas for personal brainstorming and diagrams. Research collection is a secondary workflow. This assumption is revisited below.

Priorities weigh task blockage, frequency/reach, the current product promise, local evidence, implementation scope, and ongoing maintenance. The ordering is qualitative. **Next** means start here; **After core** extends ordinary workflows; **Profile first** is an investigation queue, not permission to implement an unmeasured optimization; **Later** needs stronger demand. Ranks express importance, not a mandatory serial implementation schedule.

Those features strengthen the case for bounded sizing and source links, while showing why full linked-note semantics are more work than an Open URL command.

[JSON Canvas 1.0](https://jsoncanvas.org/spec/1.0/), [Qt Quick performance guidance](https://doc.qt.io/qt-6/qtquick-performance.html), [Qt wheel events](https://doc.qt.io/qt-6/qml-qtquick-wheelevent.html), and [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) provide additional format, runtime, and interaction references. Web accessibility dimensions are design guidance here, not a claim about native-app compliance.

## Assumptions challenged

| Assumption | Finding and resulting decision |
|---|---|
| Every category must contain exactly five items. | The quota hid cross-cutting gaps and encouraged weak additions. Keep one ranked list and overlapping category tags. |
| A feature common in competitors must be needed here. | Rejected. A source establishes that a pattern exists. Demand, workflow fit, and maintenance still determine priority. Every row therefore includes a counterargument. |
| No user study means defer every feature. | Also rejected. Code establishes that object copying loses structure and connectors lack labels. These are coherent core-workflow gaps; observation should refine scope rather than indefinitely block them. |
| Omarchy users only need keyboard interaction. | Unsupported. The app explicitly supports the mouse. The wheel branch mishandles a pure horizontal delta by inspection; actual device delivery still needs a live check. |
| Keyboard support proves screen-reader accessibility. | False. There is no explicit per-item accessibility contract; some text may still be implicitly exposed. Audit object identity, reading order, selection, relations, and announcements before prescribing the architecture. |
| Local-first alone differentiates the product. | Rejected by Excalidraw and AFFiNE's own descriptions. Omarchy integration, quick local capture, keyboard workflow, transparent files, and narrow scope are the stronger proposed positioning. This is not a measured preference study. |
| More visual effects will improve the board. | Unproven. Prefer hierarchy, useful connector labels, alignment, and readable targets. Do not add a reskin, shadows, more colors, or animations without a specific problem. |
| The board lacks selection distinction or overflow feedback. | Incorrect. Cursor and marked-item rings already differ, and overflow has an indicator. The narrower issues are low-zoom hit targets and an explicit fit-height action. |
| Native JSON means other tools can edit the board. | Incorrect. The schema is proprietary to this application; JSON Canvas requires an adapter and explicit handling of unsupported content. Native export already covers sharing with another Omarchyform user. |
| Offscreen items are already free. | Incorrect. Rendering is culled and several heavy parts are lazy, but the Repeater still instantiates every Node, text preview bindings remain, and image sources are assigned. Which cost dominates needs profiling. |
| A spatial index fixes all connector slowness. | Incorrect. It can reduce candidate scanning in sparse views. Dense-view rasterization is a separate measured cost. Current plain-model caches and retained pan rendering must not be proposed as missing work. |
| A GPU rewrite is the obvious next performance change. | Not established. Earlier quadratic path work has already been removed. Compare dense rendering alternatives against current code and preserve crossing transparency before choosing a backend. |
| A worker makes large files load faster. | Not necessarily. It may reduce main-thread blocking while adding transfer overhead. First separate the safety scan, parsing, copying, model construction, serialization, and I/O. |
| Async image loading and input limits solve image memory. | Not established. Async decoding is not a retention budget. The documented foreign-import aggregate budget does not cover subsequent local editing, all existing boards, split panes, or export scenes; see [security-review.md](security-review.md). Measure those paths. |
| Fewer undo steps adequately bound undo cost. | Not established by item-count-based depth. Snapshot bytes and restore churn are separate questions. Profile them, and preserve document ownership and one-step gesture semantics. |
| Undo optimization means bringing back timeline/history. | False. In-session undo already exists. Persisted edit history was removed after excessive costs; optimizing the former does not justify restoring the latter. |
| A hostile-test ceiling is a good responsiveness target. | False. Existing 2-second limits and exceptions are regression ceilings. Record worst pauses and time-to-editable separately, then choose targets for representative hardware and workloads. |
| Public issue reports are all current defects. | Incorrect. [Issue #57](https://github.com/thepixelgardener-create/omarchyform/issues/57) is closed, and `applyPayload` now applies changed window-mode preferences. Do not re-add that fix to the backlog. |
| The initial audience assumption is certain. | It is provisional. Research-heavy use raises links, content search, and interchange. Diagram-heavy use raises connectors and guides. Image-heavy use raises decode/retention work. Frequent huge boards move profiling ahead of cosmetic work. Pen/PDF-heavy use may indicate a different tool is a better fit. |

## What was removed or not added

| Candidate | Decision | Reason / condition for revisiting |
|---|---|---|
| Orthogonal/elbow routing as an immediate visual improvement (old V4) | Remove from the near-term list | Selectable, labeled, editable straight connectors complete more of the basic workflow first. Revisit with dense-diagram examples showing crossings are the actual obstacle; preserve manual control. |
| A dedicated GPU/scene-graph rewrite as the selected speed fix (old S4) | Remove the predetermined solution; retain an experiment under #20 | The current remaining dense raster cost is real, but neither a backend migration nor a particular speedup is established. [Qt's renderer](https://doc.qt.io/qt-6/qtquick-visualcanvas-scenegraph-renderer.html) also makes ordering and blending constraints relevant. |
| Real-time multiplayer, cloud accounts, comments, enterprise facilitation | Do not add to this roadmap | These turn a small local plugin into a service and collaboration product. Reconsider only with a deliberate audience change. |
| An AI-generation/chat panel | Do not add by competitor imitation | The existing CLI already permits external automation. A built-in model/network/product surface needs a demonstrated workflow advantage. |
| Markdown/HTML rendering, embedded websites, transclusion, PDF annotation | Do not bundle into source links or text hierarchy | These greatly expand rendering, persistence, and input-cost responsibilities. Plain text is a deliberate current invariant. Start with a bounded explicit reference field. |
| Freehand drawing, pen-first UX, mobile parity | Keep outside this pass | Rnote and Xournal++ illustrate the depth of that workflow. This is a product expansion, not a small missing whiteboard control. |
| External drag-and-drop through the existing Qt path | Keep disabled | The contribution rules document unbounded payload retrieval. A picker can reuse validated imports; drag-and-drop needs a genuinely bounded transport first. |
| Persistent edit timeline, broad custom CSS, a template marketplace | Do not restore/add now | Respect the removed history design, maintain theme integration, and test a small local template/fragment workflow before creating extensibility systems. |

## Validation that can change this order

1. **Core tasks:** observe creating a small connected diagram, copying a cluster to a second board, reopening recent work, finding a remembered phrase, adding a disk image, and sharing the result. Ask about existing work before suggesting tasks so the session does not manufacture demand.
2. **Access and navigation:** test a mouse wheel, horizontal wheel/trackpad events, precise trackpad deltas, keyboard-only use, Orca/AT-SPI content navigation, and actual IME composition. Test 20%, 100%, and high zoom, plus overlapping hit targets. A source-code finding is not a device test.
3. **Representative performance:** include ordinary small/medium boards as well as 5,000 items and 20,000 links. Measure the live Wayland/GPU path at normal and high DPI; record median/p95/worst frame, worst uninterrupted pause, and time-to-editable separately.
4. **Missing workloads:** measure large and repeated images, offscreen images, shared/independent split panes, exports, undo/redo, reloads, and saves. Record process memory as well as time. Repeated filenames are not proof of shared decoded storage.
5. **Dense versus sparse:** compare connector candidate counts and geometry cost with raster cost. Test grids on and off, image-heavy versus text-heavy boards, and stacked all-visible items versus dispersed items. A single fixture cannot validate every rendering strategy.
6. **Acceptance:** preserve current output, cancellation, stale-result handling, ownership, plain-text behavior, file bounds, and read-only loading. Any implemented feature must follow [contributing.md](contributing.md), including real QML regressions and cost traces where applicable. These are future implementation checks, not tests claimed by this research.
